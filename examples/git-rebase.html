git rebase, at altitude

What is it? Start here. What a rebase does, in pictures. No git knowledge needed.

Rebase moves your work to the end of the line.

Same changes. They now start from the newest version of main.

Your changes get copied, not moved.

Every change gets a new ID. That one fact explains every rule below.

Why bother? One straight line is easier to read.

Merging also works. It keeps the true shape. Rebasing keeps a tidy one.

If two edits clash, git stops and waits for you.

It stops on one change at a time. You might stop more than once.

You can't lose your work by accident. There's a safety net.

If a rebase goes wrong, you can get the old version back.

The one big risk: don't rebase a branch someone else uses.

Rebase only branches that only you work on.

Already shared it? Overwrite it, with a safety catch.

The server still has the old IDs, so a plain push is refused. That's expected.

First time? Five steps, and an undo button.

Mid-way and unsure? Undo. You're exactly where you began.

How does it work? Read this if the 10k view made sense and you want the moving parts.

The 10k view showed your changes getting copied to the end of main. Here's what does the copying: git finds where you split off, lists your commits, replays each one onto main's tip, then moves your branch name to the last copy.

The parts

Branch name

feature/login is a label pointing at one commit. Rebase builds new commits, then moves this label to the last one. Nothing else moves. main stays exactly where it was.

Merge base

The last commit your branch and main share. Everything after it on your side is "your work". Everything after it on main's side is what you're catching up to.

Replay list

The commits on your branch that aren't on main: main..feature/login, oldest first. Merge commits are dropped and their changes flattened, unless you pass --rebase-merges. Commits already on main (same change) get skipped.

The replay

Git checks out main's tip with a detached HEAD and applies each commit's change, one at a time, like a cherry-pick. Each result is a new commit with a new hash. Your author name, date, and message carry over. The committer date becomes now.

The stop

If a change doesn't apply cleanly, git pauses on that one commit, marks the clashing files, and hands control to you. You fix, git add, then --continue. Or --skip that commit. Or --abort the whole thing.

The finish

Git moves feature/login to the last copy and checks it out. It writes ORIG_HEAD and a reflog entry, both pointing at your old tip. That's the safety net from the 10k view.

The server copy

origin/feature/login still points at the old commits. Your new commits don't descend from them, so a normal push is refused as "non-fast-forward". You need a force-push.

Interactive mode

git rebase -i shows you the replay list in an editor first. You can reorder, squash, reword, or drop commits before replay starts.

What should we decide? Read this if you're about to run it and need to make a call. The risks, the trade-offs, and what I'd do.

My call: if feature/login is yours alone, fetch, rebase onto origin/main, run your tests, and push with --force-with-lease. If anyone else has pulled or built on the branch, merge main in instead.

Decision 1: rebase or merge?

RebaseMerge main in
History shapeOne straight line. Easy to read, bisect, and review commit by commit.True shape, with a merge commit each time you sync.
Commit hashesAll of yours change.None change.
Push afterNeeds a force-push if already pushed.Normal push.
ConflictsResolved per commit. Can stop several times.Resolved once, in the merge commit.
Safe on shared branchesNo. Others end up with duplicate commits.Yes.
Undo--abort mid-way, reflog after.git merge --abort mid-way, git reset after.

Decision 2: how to push after rebasing

OptionWhat it doesUse it?
git pushRefused: your branch no longer descends from the server's copy.Won't work. That's expected.
git push --forceOverwrites the server branch no matter what's there. Silently deletes any commit someone else pushed since you last fetched.Avoid.
git push --force-with-leaseOverwrites only if the server branch still matches your last-fetched origin/feature/login. Otherwise refused as "stale info".Yes. Default choice.

Lease gotcha: the lease checks against your last fetch. If you run git fetch right before pushing, you "accept" whatever is on the server, and the lease passes even if you never looked at it. If you fetch, check git log feature/login..origin/feature/login first. Git 2.30 and later also offer --force-if-includes to close this gap.

Decision 3: when it stops on a conflict

CommandPick it whenWatch out
--continueYou fixed the files and ran git add on them.Git opens your editor for the message. Save and close it.
--skipThis commit isn't needed any more, such as when main already has the same fix.Drops that commit's changes. Not a "fix later" button.
--abortYou're unsure, tired, or the conflict is bigger than expected.Nothing. You're back to the exact pre-rebase state.

Decision 4: squash first?

What could go wrong

Edge caseWhat happensDo this

The plan

  1. Commit or stash everything. Check git status is clean.
  2. git fetch origin.
  3. Optional: note your tip with git rev-parse --short HEAD. The reflog has it too.
  4. git rebase origin/main. On each stop: fix, git add, git rebase --continue. If it goes sideways, git rebase --abort.
  5. Build and run tests. A clean rebase can still produce code that doesn't work together.
  6. git push --force-with-lease.

Setup: the demo function

Builds this history: main has Initial app then Add footer. feature/login split off after Initial app and has two commits.

demo() {
  cd "$(mktemp -d)" || return
  git init -q -b main
  git config user.name alice
  git config user.email alice@example.com
  echo v1 > app.txt; git add app.txt; git commit -qm "Initial app"
  git switch -qc feature/login
  echo "login form" > login.txt; git add login.txt; git commit -qm "Add login form"
  echo "check password" >> login.txt; git commit -qam "Validate password"
  git switch -q main
  echo footer > footer.txt; git add footer.txt; git commit -qm "Add footer"
  git switch -q feature/login
}

P8The lease catches someone else's push

bob pushes a commit to the branch after alice's last fetch. alice then rebases and tries to push.

demo
R="$(mktemp -d)/server.git"; git init -q --bare "$R"
git remote add origin "$R"; git push -q -u origin main feature/login
B="$(mktemp -d)/bob"; git clone -q -b feature/login "$R" "$B"
( cd "$B" && git config user.name bob && git config user.email bob@example.com \
  && echo "remember me" > remember.txt && git add remember.txt \
  && git commit -qm "Add remember-me" && git push -q )
git rebase -q main
git push --force-with-lease
git push --force
git fetch -q; git log --oneline origin/feature/login | grep -c remember
 ! [rejected]        feature/login -> feature/login (stale info)
error: failed to push some refs to '…/server.git'
 + 1a2b3c4...d4e3f2a feature/login -> feature/login (forced update)
0

Look at: the lease refused because the server moved since alice's last fetch. Plain --force went through, and the count of bob's commit on the server is now 0. It's gone from the branch.

P9Rebasing a shared branch duplicates commits

bob builds on the pushed branch. alice rebases and force-pushes. bob pulls.

demo
R="$(mktemp -d)/server.git"; git init -q --bare "$R"
git remote add origin "$R"; git push -q -u origin main feature/login
B="$(mktemp -d)/bob"; git clone -q -b feature/login "$R" "$B"
( cd "$B" && git config user.name bob && git config user.email bob@example.com \
  && echo "remember me" > remember.txt && git add remember.txt \
  && git commit -qm "Add remember-me" )
git rebase -q main; git push -q --force-with-lease
cd "$B"; git pull -q --no-rebase --no-edit
git log --oneline | grep "Add login form"
5b6c7d8 Add login form
3c1d2e4 Add login form

Look at: the same commit twice, once per hash. bob's merge stitched the old copies back in. If he pushes, everyone gets both. This is why the 10k view calls it the one big risk.

P11How long the safety net lasts

The old commits are "unreachable" after a rebase: no branch points at them. Their reflog entries expire on the gc.reflogExpireUnreachable clock. Unset config means the default applies.

git config --get gc.reflogExpire               # empty = default 90 days
git config --get gc.reflogExpireUnreachable    # empty = default 30 days
git help config   # search for reflogExpireUnreachable

Look at: both print nothing on a stock setup, so the documented defaults (90 and 30 days) apply. Garbage collection can delete the commits only after their reflog entries expire.

Alternatives considered

AlternativeWhy not the default here
Merge main into the branch (P5)Safe and fine. Adds a merge commit per sync. The right call when the branch is shared.
git pull --rebaseRebases your local commits onto the server copy of the same branch. Useful for syncing with teammates, not for moving onto main.
Squash-merge in the pull requestGives main one clean commit with no local rebase. You still need to sync with main if there are conflicts.
git push --forceErases others' pushes without warning (P8).
Never update the branchConflicts land on the reviewer or the merge button instead of on you.
